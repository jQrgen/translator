    I'll fetch that Nexa forum thread and summarize it for you.# Summary of the Nexa forum post "Scaling By Circuit" **Source**: https://forum.nexa.org/t/scaling-by-circuit/1749 (official Nexa forum, second article in the hardware project series) Nature**: long technical article + illustrations (including 5 architecture diagrams), the core being the argument for **"achieving Bitcoin-style scaling with circuits/hardware"**, with the main arguments drawn from Nexa Chief Scientist Dr. Peter Rizun's talk at the Australian Crypto Convention in Sydney in November 2024. --- ## I. The main thread: ticking the boxes for a "better Bitcoin" The first article in the series built Nexa's validation engine out of "six components + a tape + a head," proving it is **pipelineable**. This article ticks off the remaining three boxes, needing **only three changes**, and throws in two properties for free: | Property | Source | Notes | |---|---|---| | Pipelineable | Tape moves one way only | Proven in article one | | Scalable | Parallel pipelines + "set tree" | Change #1 in this article | | Extensible | Feedback loop → Turing machine | Derived here (an unexpected bonus) | | Compressible | UTXO commitment written into the block header | Change #2 in this article | | Incentive compatible | Hash function forces the full validation process to run | Topic of article one (change #3) | --- ## II. Four technical points ### 1. Two pipelines (parallelization) — solving race conditions with an "inverted clock" - Add a second parallel validation pipeline, with a switch routing transactions to whichever one is idle. - Difficulty one: the two heads share the same UTXO set; if both try to spend the same coin in the same clock cycle you get a **race condition**. - Solution (pure hardware): **invert the clock signal of the second pipeline** — one grabs coins on the rising edge, the other on the falling edge, making it physically impossible to access the same coin simultaneously. Minimalist, but very elegant. ### 2. A "set tree" replacing the Merkle tree — the key change in this article - Difficulty two: after parallelization the **output order may differ from the input order** (TX2 may enter the block before TX1). Peer nodes recompute a different root hash → the block is judged invalid. - The traditional fix is **sorting**, but sorting is not pipelineable (the tape would have to move back and forth) → **sorting cannot scale**. - The author argues the "Merkle tree" in Satoshi's whitepaper should be understood by **intent rather than the letter** — what he wanted was not a "tree of a list" but a **"tree of a set."** The real answer is a **compact bitwise prefix tree**: - It still supports SPV proofs; - and is **independent of transaction order** — as long as two transaction sets are equal, the root hashes are equal. - This builds on **Amaury Séchet**'s (BCH core developer) idea of "hashing a block as a set rather than a list." - With it, **pipelineability is restored without sorting** → one change makes the coin "scalable." > The scaling formula the author gives: under pipelining, the TPS ceiling ≈ **the reciprocal of the slowest step (usually signature verification)**; other short latencies don't matter; under parallelization, throughput can be **multiplied by the number of pipelines**. Rizun's own words: *"Basically we can just throw more hardware at the problem and reach any scale."* ### 3. The "accidental Turing machine" — extensibility from the feedback loop - Scenario: Alice→Bob, and Bob immediately pays the same coin to Carol. Because ordering can't be controlled, the head may see Bob→Carol **first**: looking up the UTXO set it can't find the coin, but it can't find proof it was "spent" either → **it can be judged neither valid nor invalid = undecided**. - Solution: add a **third pipeline** that **feeds undecided transactions back to the input**. On re-entry, Bob's coin has already been written into the UTXO set and the transaction validates normally. - It's precisely the "existence of an undecided state" that forces a feedback path, and the feedback path lets the machine **simulate a Turing machine**: the head can move left and right, can insert new cells, and the tape length is effectively unbounded. - Practical significance**: new features such as quantum-resistant signatures can be added **purely via script**, with **no soft or hard fork needed → the coin becomes "extensible."** ### 4. "Proofs instead of a database" — compressibility - Status quo: fully validating nodes must maintain their own UTXO set to judge whether a coin is unspent. - Change #2: miners store the UTXO set as a compact bitwise prefix tree and **put that tree's root hash into the block header** (right next to the block root hash). - The idea comes from the 2012 BitcoinTalk "ultimate blockchain compression" thread. - From then on, a full node only needs **one branch proof up to the block header** to confirm a coin is unspent, and **no longer needs a UTXO database**. - Computing the UTXO root hash isn't hard for miners: it's pipelineable, parallelizable, and each insert/delete is O(log s) → it fits the definition of "scalable." --- ## III. UTXO model vs account model (Nexa vs Ethereum) This is the closing comparison of the article, and also the root cause of "where the parallelism comes from": | Dimension | Nexa (UTXO) | Ethereum (accounts) | |---|---|---| | State model | Only "coins," spent in full or not at all | Accounts + balances | | Scope of state change | **Localized** to the specified inputs | The head sits in a global state space and can read/write anything | | Parallelism | **High** — you can know in advance which state region each transaction can change, so multiple heads don't conflict | **Low** — the state region a transaction can touch cannot be localized | | Risk | Inputs are essentially a "firewall" | When a contract is messy, Eve might write a transaction that deducts from Alice's account and pays Eve | | Positioning | A coin/commodity, confirmed by miners' PoW | Ether is "shares in a decentralized company," neither a coin nor a commodity | The author's conclusion: **they are two different things serving different purposes**; there's no simple better/worse. --- ## IV. Overall conclusion > "On paper, this engine is already complete: a better Bitcoin, box by box ticked, made of wires and gates.
