The through-line: ticking the boxes for a "better Bitcoin" The first article in the series built Nexa's validation engine out of "six components + a tape + a head" and proved it is **pipelineable**. This article fills in the remaining three ticks, needing **only three changes**, and throws in two properties for free: | Property | Source | Notes | |---|---|---| | Pipelineable | Tape flows in one direction | Proven in part one | | Scalable | Parallel pipelines + "set tree" | Change #1 in this article | | Extensible | Feedback loop → Turing machine | Derived here (a happy accident) | | Compressible | UTXO commitment written into the block header | Change #2 in this article | | Incentive compatible | Hash function forces the validation process to run to completion | Theme of part one (change #3) | --- ## II. Four technical points ### 1. Two pipelines (parallelization) — solving the race condition with an "inverted clock" - Add a second parallel validation pipeline and use a switch to route transactions to whichever one is idle. - Difficulty one: the two heads share the same UTXO set, and if both try to spend the same coin in the same clock cycle you get a **race condition**. - Solution (pure hardware): **invert the clock signal of the second pipeline** — one grabs coins on the rising edge, the other on the falling edge, making it physically impossible to access the same coin simultaneously. Minimalist, but very elegant. ### 2. A "set tree" replacing the Merkle tree — the key change in this article - Difficulty two: after parallelization the **output order of transactions may differ from the input order** (TX2 may enter the block before TX1). Peer nodes recompute a different root hash → the block is judged invalid. - The traditional fix is **sorting**, but sorting can't be pipelined (the tape has to move back and forth) → **sorting can't scale**. - The author argues: the "Merkle tree" in Satoshi's whitepaper should be understood by **intent rather than the letter** — what he wanted was not a "tree of a list" but a **"tree of a set"**. The real answer is a **compact bitwise prefix tree**: - It still supports SPV proofs; - And it is **order-independent** — as long as two transaction sets are equal, the root hashes are equal. - This builds on **Amaury Séchet**'s (BCH core developer) idea of "hashing a block as a set rather than a list". - With it, **pipelineability is restored without sorting** → one change makes the coin "scalable". > The scaling formula the author gives: under pipelining, the TPS ceiling ≈ **the reciprocal of the time taken by the slowest step (usually signature verification)**, and other short latencies don't matter; under parallelization, throughput can be **multiplied by the number of pipelines**. Rizun's own words: *"Basically we can reach any scale just by throwing more hardware at the problem."* ### 3. "The accidental Turing machine" — extensibility comes from the feedback loop - Scenario: Alice→Bob, and Bob immediately pays the same coin to Carol. Because the order can't be controlled, the head may see Bob→Carol **first**: it looks up the UTXO set and can't find the coin, but also can't find evidence it was "spent" → **it can judge it neither valid nor invalid = undecided**. - Solution: add a **third pipeline** to **feed undecided transactions back to the input**. On re-entry Bob's coin has already been written into the UTXO set, so the transaction validates normally. - It is precisely the "existence of an undecided state" that forces a feedback path, and the feedback path makes the machine **able to simulate a Turing machine**: the head can move left and right, can insert new cells, and the tape length is effectively unbounded. - Practical meaning**: new features such as quantum-resistant signatures can be added **purely in script**, **without even a soft or hard fork → the coin becomes "extensible"**. ### 4. "Replacing the database with proofs" — compressibility - Status quo: fully validating nodes must maintain their own UTXO set to judge whether a coin is unspent. - Change #2: miners store the UTXO set as a compact bitwise prefix tree and **put that tree's root hash into the block header** (right next to the block root hash). - The idea comes from the 2012 BitcoinTalk thread on "ultimate blockchain compression". - From then on a full node only needs **a single branch proof up to the block header** to confirm a coin is unspent, and **no longer needs a UTXO database**. - Computing the UTXO root hash isn't hard for miners: it's pipelineable, parallelizable, and each insert/delete is O(log s) → it fits the definition of "scalable". --- ## III. UTXO model vs. account model (Nexa vs. Ethereum) This is the article's closing comparison, and also the root cause of "where the parallelism comes from": | Dimension | Nexa (UTXO) | Ethereum (accounts) | |---|---|---| | State model | Only "coins", spent in full or not at all | Accounts + balances | | Scope of state changes | **Localized** to the specified inputs | The head sits in the global state space and can read/write anything | | Parallelism | **High** — you can know in advance which region of state each transaction can change, so multiple heads don't conflict | **Low** — the state region a transaction can touch can't be localized | | Risk | Inputs are essentially a "firewall" | If a contract is messy, Eve may be able to write a transaction that debits Alice's account and pays Eve | | Positioning | A coin/commodity, confirmed by miners' PoW | Ether is "shares in a decentralized company", neither a coin nor a commodity | The author's conclusion: **the two are different things serving different purposes**; there's no simple better-or-worse. --- ## IV. Overall conclusion > "On paper, the engine is now complete: a better Bitcoin, box by box, made of wires and gates. What remains is building it in **real silicon you can hold in your hand** — which is exactly where this series goes next." **In one sentence**: this article uses a **circuit-level hardware architecture** to argue why Nexa is naturally scalable — **parallel pipelines (inverted clock) + set tree (sorting-free) + UTXO local state + feedback loop (Turing completeness) + UTXO commitment in the block header** — with all five together yielding a "scalable, extensible, compressible, incentive-compatible" improvement on Bitcoin, and it previews the next installment moving on to **real chip implementation**. **Cited sources**: Peter Rizun's Sydney talk (2024-11-23); the 2012 BitcoinTalk "ultimate blockchain compression" thread; Amaury Séchet's set-hashing idea; the SPV section of Satoshi's whitepaper; earlier pieces in the series, "Why Nexa Builds Hardware" and "A Node Made of Wires".”

Because the order can't be controlled, the head may see Bob→Carol **first**: it looks up the UTXO set and can't find the coin, but also can't find evidence it was "spent" → **it can judge it neither valid nor invalid = undecided**. - Solution: add a **third pipeline** to **feed undecided transactions back to the input**. On re-entry Bob's coin has already been written into the UTXO set, so the transaction validates normally. - It is precisely the "existence of an undecided state" that forces a feedback path, and the feedback path makes the machine **able to simulate a Turing machine**: the head can move left and right, can insert new cells, and the tape length is effectively unbounded. - Practical meaning**: new features such as quantum-resistant signatures can be added **purely in script**, **without even a soft or hard fork → the coin becomes "extensible"**. ### 4. "Replacing the database with proofs" — compressibility - Status quo: fully validating nodes must maintain their own UTXO set to judge whether a coin is unspent. - Change #2: miners store the UTXO set as a compact bitwise prefix tree and **put that tree's root hash into the block header** (right next to the block root hash). - The idea comes from the 2012 BitcoinTalk thread on "ultimate blockchain compression". - From then on a full node only needs **a single branch proof up to the block header** to confirm a coin is unspent, and **no longer needs a UTXO database**. - Computing the UTXO root hash isn't hard for miners: it's pipelineable, parallelizable, and each insert/delete is O(log s) → it fits the definition of "scalable". --- ## III. UTXO model vs. account model (Nexa vs. Ethereum) This is the article's closing comparison, and also the root cause of "where the parallelism comes from": | Dimension | Nexa (UTXO) | Ethereum (accounts) | |---|---|---| | State model | Only "coins", spent in full or not at all | Accounts + balances | | Scope of state changes | **Localized** to the specified inputs | The head sits in the global state space and can read/write anything | | Parallelism | **High** — you can know in advance which region of state each transaction can change, so multiple heads don't conflict | **Low** — the state region a transaction can touch can't be localized | | Risk | Inputs are essentially a "firewall" | If a contract is messy, Eve may be able to write a transaction that debits Alice's account and pays Eve | | Positioning | A coin/commodity, confirmed by miners' PoW | Ether is "shares in a decentralized company", neither a coin nor a commodity | The author's conclusion: **the two are different things serving different purposes**; there's no simple better-or-worse. --- ## IV. "意外的图灵机"——扩展性来自反馈回路 - 场景：Alice→Bob，Bob 立刻把同一枚币付给 Carol。因为顺序不可控，磁头可能**先**看到 Bob→Carol：查 UTXO 找不到该币，但也找不到"已花费"的证据 → **既不能判有效也不能判无效 = 未决（undecided）**。 - 解法：加**第三条流水线**把未决交易**回灌到输入端**。重入后 Bob 的币已被写入 UTXO 集，交易即可正常验证通过。 - 正是"存在未决状态"逼出了反馈路径，而反馈路径让机器**可模拟图灵机**：磁头能左右移动、能插入新格，磁带长度实际无界。 - 实用意义**：可**纯用脚本**加入量子抗性签名等新特性，**连软/硬分叉都不需要 → 币变得"可扩展"。 ### 4. "用证明代替数据库"——可压缩性 - 现状：全验证节点必须自维护 UTXO 集来判断币是否未花费。 - 第 2 处改动：矿工把 UTXO 集存为紧凑位前缀树，**把该树根哈希放进区块头**（紧挨着区块根哈希）。 - 思想源自 BitcoinTalk 2012 年"终极区块链压缩"帖。 - 全节点此后只需**一条到区块头的分支证明**即可确认币未花费，**不再需要 UTXO 数据库**。 - 矿工计算 UTXO 根哈希不难：可流水线、可并行、每次增删 O(log s) 复杂度 → 符合"可扩容"定义。 --- ## 三、UTXO 模型 vs 账户模型（Nexa vs 以太坊） 这是全文的收尾对比，也是"并行度从哪来"的根因： | 维度 | Nexa（UTXO） | 以太坊（账户） | |---|---|---| | 状态模型 | 只有"币"，全花或全不花 | 账户 + 余额 | | 状态改动范围 | **局部化**到指定输入 | 磁头身处全局状态空间，可读写一切 | | 并行性 | **高**——可预知每笔交易能改的状态区域，多磁头无冲突 | **低**——交易可触及的状态区域无法局部化 | | 风险 | 输入本质上是"防火墙" | 合约混乱时，Eve 可能写出扣 Alice 账户给 Eve 的交易 | | 定位 | 币/商品，矿工 PoW 确认 | Ether 是"去中心化公司的股份"，非币非商品 | 作者结论：**两者是服务不同目的的两种东西**，不存在简单优劣。 --- ## 四、总体结论 > "纸上，这台引擎已经完整了：一个更好的比特币，逐项打勾，由导线和门电路构成。剩下的就是把它用**你能握在手里的真硅**造出来——那正是本系列下一步的方向。" **一句话**：这篇文章是用**电路级硬件架构**论证 Nexa 为何天然可扩容——**并行流水线（反相时钟）+ 集合树（免排序）+ UTXO 局部状态 + 反馈回路（图灵完备）+ 区块头 UTXO 承诺**，五者合力得到"可扩容、可扩展、可压缩、激励相容"的比特币改良方案，并预告下一篇进入**真实芯片实现**。 **引用来源**：Peter Rizun 悉尼演讲（2024-11-23）；BitcoinTalk 2012"终极区块链压缩"帖；Amaury Séchet 的集合哈希思路；中本聪白皮书 SPV 部分；系列前作《Why Nexa Builds Hardware》《A Node Made of Wires》。
